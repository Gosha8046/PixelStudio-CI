# Архитектура PixelStudio CI

## Слои и зависимости

- **Core** ничего не знает об интерфейсе, JavaScript, файловой системе и платформе. Весь код рисования, слоёв, кадров, истории и экспорта здесь, и он одинаково выполняется в обоих хостах.
- **UI** — общий интерфейс на Razor-компонентах. JavaScript в нём только переносит готовые RGBA-буферы на `<canvas>`, рисует оверлеи (сетку и перекрестие) и передаёт ввод. Логики документа в JS нет.
- **Хосты** — тонкие адаптеры: точка входа, регистрация сервисов и платформенная работа с файлами.

`Platform/` разнесён осознанно: контракты лежат в UI, реализации — в хостах. Это единственные интерфейсы в проекте. Они нужны потому, что файловые операции браузера и Windows принципиально различаются.

## Модель данных

```
SpriteDocument
├── Width, Height                     фиксированы для всех слоёв и кадров (1–512)
├── Layers: LayerManager              общий стек слоёв; индекс 0 = нижний
│   └── Layer { Id, Name, Visible, Opacity 0–100 %, BlendMode }
├── Timeline                          порядок кадров, FPS, Loop
│   └── Frame { Id, DurationMs?, Cels: Dictionary<LayerId, Canvas> }
│                                    ровно один Canvas на пару (кадр, слой)
├── Palette { Colors ≤ 64 }
└── History: UndoHistory
Canvas { Width, Height, Color32[] Pixels }   плоский массив, index = y·Width + x
Color32 { R, G, B, A }                        8 бит на канал, sRGB, прямая (не премультиплицированная) альфа
```

- `Id` слоёв и кадров стабильны: они не меняются при перестановке и сохраняются в файле. Cel'ы адресуются по `(frameId, layerId)`, а не по индексам.
- **Дублирование** слоя или кадра всегда делает `Canvas.Clone()` с новым массивом. Общих изменяемых буферов нет, это проверено тестами.

## Композиция и смешивание

1. Хранение: sRGB, 8 бит, прямая альфа. Гамма-линеаризации нет, как в большинстве пиксельных редакторов.
2. Порядок: от слоя 0 (нижний) вверх, начиная с полностью прозрачного фона. Скрытые слои и слои с непрозрачностью 0 пропускаются.
3. Эффективная альфа источника: `αs = A/255 · opacity/100`.
4. Функция смешивания `B(Cb, Cs)`: Normal = `Cs`; Multiply = `Cb·Cs`; Screen = `Cb + Cs − Cb·Cs`.
5. Формула W3C Compositing Level 1 (source-over со смешиванием):
   - `Cs' = (1 − αb)·Cs + αb·B(Cb, Cs)`
   - `αo = αs + αb·(1 − αs)`
   - `Co = (αs·Cs' + αb·Cb·(1 − αs)) / αo`

   Поверх прозрачного фона любой режим даёт сам источник.
6. Округление к ближайшему (половина вверх), ограничение 0–255; при `αo = 0` результат `(0,0,0,0)`.

Эталонные значения для тестов посчитаны **независимо**, точной рациональной арифметикой (Python `fractions`): см. `CompositorTests`.

### Объединение с нижним слоем

Для каждого кадра новый cel = изолированная композиция `[нижний слой (его opacity), верхний слой (opacity + режим)]` поверх прозрачности. Получившийся слой сохраняет id и имя нижнего, режим Normal и 100 %.

- Это **точно** сохраняет картинку, если слои Normal или под нижним слоем нет видимых пикселей. Это проверено тестами.
- Если верхний слой в режиме Multiply/Screen лежит над прозрачными участками нижнего, а под ними есть другие слои, один Normal-слой не может выразить такое взаимодействие. Так же ведут себя Photoshop и Aseprite. В этом случае `MergeDown` сравнивает композицию всех кадров до и после, возвращает `VisuallyIdentical = false` и максимальное отличие, а UI показывает предупреждение и подсказку про Ctrl+Z.

## Undo/Redo

Линейная история (`UndoHistory`, до 256 шагов) хранит два вида команд:

| Команда | Что хранит | Когда |
|---|---|---|
| `PixelEditCommand` | Прямоугольник изменённых пикселей «до» и «после» в одном cel'е | Один жест инструмента (нажатие → движения → отпускание) = одна команда |
| `StructureCommand` | Снимки `DocumentStructure` до и после: свойства и порядок слоёв, порядок и длительности кадров, **ссылки** на Canvas, FPS, Loop, палитра | Любое структурное изменение |

Снимок структуры не копирует пиксели и стоит O(слои × кадры). Это корректно благодаря инварианту: **структурные операции никогда не меняют существующие Canvas**, а только добавляют, удаляют или создают новые (дублирование, слияние). Пиксели на месте меняет только `PixelEditCommand`. Линейная история гарантирует, что такие изменения будут отменены раньше, чем восстановится структура, ссылающаяся на тот же Canvas.

Последовательные изменения непрозрачности одного слоя (перетаскивание ползунка) сливаются в один шаг до отпускания. Флаг «есть несохранённые изменения» вычисляется по позиции в истории относительно точки сохранения, поэтому Undo до сохранённого состояния снова делает документ «чистым».

## Инструменты и ввод

- JS переводит координаты указателя в пиксели документа: целочисленный zoom, pan, `floor((client − origin) / zoom)`. В обработку идут только смены пикселя под указателем; `getCoalescedEvents()` сохраняет точность быстрых кривых.
- События ставятся в очередь. В .NET одновременно уходит **не больше одного** пакета (`OnPointerBatch`), поэтому порядок событий одинаков в WebAssembly и WebView2, а события, пришедшие во время обработки, объединяются в пакет.
- `ToolController` соединяет соседние точки линией Брезенхэма: при любой скорости движения пропусков нет. На каждое движение — ноль выделений памяти (`PointerMove_DoesNotAllocate`).
- Заливка — построчная (scanline) с явным стеком, 4-связная, без рекурсии. Все пиксели с A = 0 считаются одним цветом.
- Карандаш записывает цвет «как есть» (режим замены): альфа основного цвета становится альфой пикселя. Повторный проход по пикселю в одном жесте не накапливает прозрачность.
- Горячие клавиши описаны в `KeyMap` (C#) по `KeyboardEvent.code`, поэтому работают в любой раскладке. JS не перехватывает их, пока фокус в текстовом поле.

## Конвейер отображения

```
Документ ──Compositor──► composite (RGBA) ──┬─► ViewRenderer: + Onion Skin ──► <canvas id=ps-main>  (CSS: image-rendering: pixelated)
                                            └─► Tile Preview 3×3             ──► <canvas id=ps-tile>
JS overlay (отдельный <canvas>): рамка спрайта, пиксельная сетка, Pixel Crosshair — рисуются в экранных пикселях с учётом devicePixelRatio
```

- Масштаб целочисленный (1–64×), сглаживание отключено, поэтому пиксели не размываются.
- **Инкрементальная перерисовка:** во время рисования пересчитывается и выгружается только изменённый прямоугольник (`ViewRenderer.RenderRegion`). «Призраки» соседних кадров кэшируются. Полный пересчёт идёт при смене кадра, отмене, структурных изменениях и смене настроек. Замеры приведены в README.
- Сетка, перекрестие, Onion Skin и Tile Preview живут только в слое отображения. `Exporter` использует `Compositor` напрямую и физически не может их получить.

## Платформенные различия

| | Браузер (WebAssembly) | Windows (WebView2) |
|---|---|---|
| Выполнение C# | .NET runtime на WebAssembly: интерпретатор или AOT | Нативный .NET 10 (JIT) |
| Отображение | DOM + Canvas 2D браузера | Тот же HTML/Canvas в WebView2 |
| Открыть | `<input type=file>` | `OpenFileDialog` |
| Сохранить | Скачивание файла (Blob + `<a download>`) | `SaveFileDialog`, Ctrl+S пишет в тот же файл; запись атомарна через временный файл |
| Несохранённые изменения | `beforeunload` (браузер показывает свой диалог) + диалог в приложении | `FormClosing`: «Сохранить / Не сохранять / Отмена» + диалог в приложении |
